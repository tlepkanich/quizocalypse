Two flows, one modal

The same rule builder, opened from two places with two different jobs. In onboarding the merchant is finishing a list — the groups they confirmed on the Recommendations step — so those groups are the band, with their coverage on show and the catalogue behind one button. In the standalone builder nobody is finishing a list; the catalogue is open from the start. Everything above the products band is identical in both. All measured live.

Onboarding — finish the list

The band is the merchant’s own recommendation groups and nothing else: what they confirmed on step 1, how many rules each already carries, and how far through the list they are. firming is outlined because nothing points at it yet. Add it and hit Create & add another — the meter fills and acne goes 2 rules → 3.

What the band does

  • Titled Your recommendations — not a filter chip among six, the content itself
  • The header is a plain fraction: 2/3 have a rule, amber while there is a gap and green with a tick at 3/3. No progress graphic — the number is the fastest read there is
  • Uncovered groups sort to the front and carry an amber wash, an amber border and a Needs a rule chip. Covered ones go green — a lighter wash, a green edge and a ✓ 2 rules chip — so they read as done, skip these without being read at all. Three signals in both cases: position, colour and words
  • The status takes the slot the SET tag used to hold — in this band every card is a recommendation, so the kind tag was saying nothing. That also keeps the status on one line: cards widened to 248px and the count line is just 9 products
  • The count opens the group. Click 9 products on any card for Inside firming — the products it holds, with a + N more tail. It is its own control: opening the list never selects the card, and clicking inside the list never closes it
  • Cards move between the two states only when a rule is actually saved — never while you are picking, so nothing jumps under the cursor
  • No kind tabs, no search, until asked for — the six controls that were sitting there are not part of this job
  • Past six groups the list wraps anyway, so it splits into labelled Needs a rule and Has rules sections; below that the ordering carries it and the labels would cost a line each

Adding something else

  • + Add something else opens the catalogue under a dashed rule: tabs, search, and a one-row grid with + N more
  • The recommendation groups stay above it — expanding adds a section, it never replaces the list
  • Anything picked from the catalogue is pinned up with the groups, so the rule always reads in one place

What it costs

A merchant who mostly targets tags has one extra click every time. That is the deliberate trade: the flow is optimised for the person finishing the recommendation list, which in onboarding is everyone.

Rule builder — standalone

Opened from the Logic tab on a quiz that already exists. Nobody is working through a list, so the catalogue is open from the start: All by default, every kind tab and the search in reach, one row of cards and + 7 from the catalogue for the rest.

What differs

  • Opens on All, not on the recommendation groups
  • Kind tabs and search are visible from the start — no expand step
  • No no rule yet flag and no amber outline — there is no list to finish here, so an uncovered group is not a to-do. A card that does have rules still says so (2 rules), because that is a fact rather than a task
  • The group line says groups this quiz recommends; there is no “step 1” to point at

What is identical

  • Everything above the band: rows, operators, the verb, the footer, Create & add another
  • Picked targets always render first, whatever the filter
  • One row plus + N from the catalogue on the All view; filtered views are uncapped

What it costs

Nothing that onboarding needs — but a merchant who opens this on a quiz built by the funnel gets no nudge about which recommendation groups are still uncovered. The coverage text is there; the goal framing is not.

Build notes

Against app/components/studio/logicTab/CreateRuleModal.tsx
One prop, two bands Add a flow: "onboarding" | "builder" prop (default "builder"). It changes the products band only. Onboarding renders the category list with coverage and hides kindChip / search until expanded; builder renders today's band with kindChip defaulting to "all".component
Coverage For each category id, count the rules in doc.decision_rules whose target_ids contains it. Client-side derive, no new API. Never disable or hide a covered target; a target may carry several rules.derived
Not a gate Coverage is a readout. Nothing blocks saving a rule because a group is uncovered, and nothing blocks publishing — the existing publish gates are unchanged. If an uncovered group should warn at publish time, that belongs in the publish gate, not here.careful
The count is its own control Clicking a card's product count opens the group's contents; it must not toggle selection. The precedent is already in the code — .qz-crm-rescount in the pre-rework modal was a separate button beside the row for exactly this reason. Build it as a sibling button, not a span nested inside the card button (the mock nests it; React should not). The panel opens upward: this band sits at the bottom of the modal and .qz-lm clips overflow.popover
