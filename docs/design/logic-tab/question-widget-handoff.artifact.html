3The widget

3.3 Do not build what the mock shows

The mock predates decision 1. These parts of it are cut:

  • Several chips in a deciding cell. One chip, from a.target_id.
  • Per-chip × on a deciding cell. With one mapping, removing the chip is clearing the cell — one control, labelled “Clear this answer’s result”. The clear is setAnswerTarget(doc, nodeId, answerId, null), which destructure-drops the key.
  • Placing appends. It replaces.
  • Multi-select ticking, the staged draft and the “N selected” footer in the picks picker. A single-target picker can only read 0 or 1 selected, which implies more can be added. Use the footer slot for the selected recommendation’s product count instead.
  • The union product count on an answer. The count is just that bucket’s size. The union is real but it lives at the shopper’s selection, not the answer.

Two inconsistencies in the mock to resolve while building: the tray hides any bucket used by any answer, while the cell picker offers the full list — so the same bucket is un-placeable from one surface and freely placeable from the other. Two answers sharing a target is legal and, under a multi-select decider, a natural authoring move. Pick one rule and make both surfaces obey it. Separately, the mock’s browse list is unreachable when nothing overflowed, because its trigger stays hidden.

3.4 Accessibility

  • The cell is a real control: role="button", tabindex="0", Enter/Space. Nested chip and clear × are real buttons that stop propagation.
  • Picks picker rows are radios with aria-checked; narrows rows are checkboxes with aria-pressed. The difference must be announced.
  • The clear × needs a name that says what it clears, not a bare ×. It is opacity-hidden until hover, so it must appear on :focus-within.
  • Focus ring 2px solid var(--qz-accent), outline-offset: 1px, never removed. Colour is never the only signal.
  • Thumbnails are decorative — aria-hidden — until real images land.

4The engine

One function changes. resolveTarget takes the first selected mapped answer in authored order and discards the rest:

// app/lib/recommendDecider.ts:216-223 — today
const picked = decider && decider.type === "question"
  ? decider.data.answers.find((a) => selected.has(a.id) && a.target_id)
  : undefined;
const baseTargetId = picked?.target_id ?? null;

Collect all of them instead, then emit the list at the final return (:246-247):

const baseTargets = decider && decider.type === "question"
  ? [...new Set(decider.data.answers.flatMap(
      (a) => (selected.has(a.id) && a.target_id ? [a.target_id] : [])))]
  : [];
const baseTargetId = baseTargets[0] ?? null;

// …and at the return:
return {
  targetId: baseTargetId,
  ...(baseTargets.length > 1 ? { targetIds: baseTargets } : {}),
  matchedRuleId: null,
};

Four properties are load-bearing:

  • Iterate decider.data.answers, not selectedAnswerIds — a shopper who ticks the boxes in a different sequence must get a byte-identical page.
  • new Set dedupes to first occurrence. Two answers may legitimately point at the same bucket.
  • flatMap, not filter().map() — a.target_id type-narrows without a non-null assertion.
  • The length > 1 conditional spread is mandatory. It keeps single-answer resolutions shape-identical to today, which is what every toEqual in recommendDecider.test.ts and the pathEnumeration snapshot assert against.
Everything downstream already works

Reuse the existing ResolvedTarget.targetIds channel and recommendationEngine.ts needs no edit:

  • :411-419 already unions members with first-occurrence dedupe when targetIds is set.
  • :450-452 already forces targetShape: undefined for a union. This matters: without it, an anchor answer pointing at a single-product bucket sends the page down the hero-only branch (recommendDecider.ts:395-398), which computes the union and then throws it away while poolSize still reports the union size — nothing looks wrong.
  • :441-445 already sets poolAdjusted on Boolean(resolved.targetIds).
  • narrowIdsByFilters operates on a flat id list and never reads a target id, so filters narrow a union exactly as they narrow one bucket.

Two comments become false and must be rewritten, or they will mislead every future reader: ResolvedTarget.targetIds’ docblock (:34-39) says it is “set ONLY when a replace rule carries several targets” — there are now two producers. And resolveTarget’s docblock (:183-190) says it resolves “the shopper’s ONE target”. Same for quizSchema.ts:337-349, whose role comment still reads “multi-select questions are auto-qualifier (§2.2)”. All three are comment-only; no field changes.

The anchor. targetId === targetIds[0] — the first authored mapped answer the shopper selected. It anchors the rec-page config (settingsForTarget, recommendationEngine.ts:399), the persona shown above the pool (:478-480), and the synthetic pool write (:455-457). Consequence to accept deliberately: the headline and persona a shopper sees are decided by the merchant’s answer ordering. Pool order follows the same rule — anchor’s members first, then each later target’s unseen members — so with the default collection_order hero logic, the hero is the anchor bucket’s first baked member.

The action-rule branch needs nothing. A rule with an action sets actionRule and falls through to the base mapping, which now carries the union; the branch at :225-234 stays as it is.

6Routing — needs a decision

Several selected answers, several routes, one winner

A multi-select question advances using the edge_handle_id of the first checked answer in authored order — not click order, not the question default:

const first = node.data.answers.find((a) => checked[a.id]); onAdvance(selectedIds, first ? first.edge_handle_id : null) — QuestionView.tsx:410 and :423, the only two multi-select commit sites.

Every other checked answer’s route is silently discarded. Nothing merges, warns, or errors. Reordering answers in the builder silently re-routes shoppers.

This is live today, not hypothetical: Answer.edge_handle_id is required on every answer regardless of type, setAnswerRoute has no type gate, and the Logic tab renders RouteMenuButton on every answer row with no multi-select exclusion (LogicTabCard.tsx:1239). Decision 2 makes it matter, because the deciding question is where divergent routing is most likely to be authored.

The ambiguity is already acknowledged in code and shown nowhere useful: routeTrace.ts:207-212 emits a warn — “Per-answer routing on a multi-select is ambiguous when several answers are picked” — but routingConflicts is rendered only by the old ContextPanel. The Logic tab never calls it, so the surface where routes are actually authored shows nothing.

The two options

OptionCost
A. Keep first-authored-wins; surface the warning. Call routingConflicts from the Logic tab and show it on the deciding question’s rows. Low. No runtime change, no legacy risk. The rule stays implicit but stops being invisible. Recommended.
B. Disable per-answer routing on a multi-select decider. One route for the whole question; the THEN GO TO cell collapses to a single control. Medium. Unambiguous, but it removes an authorable capability from shipped docs and needs a migration story for quizzes that already use it.
Do not simply “fix” the tie-break

The first-authored-wins rule lives in shared runtime code with no logic_model branch — the same component serves legacy points/ladder docs. Changing it changes behaviour for already-published legacy quizzes at /q, and because it changes no publishedJson bytes, the byte pin stays green and will not catch it. If the tie-break must change, gate it on doc.logic_model === "decider".

No test pins the current behaviour either way — routeTrace.test.ts asserts only that the warning fires. Add a QuestionView-level test for whichever rule you choose.

Separately, publish has no gate for this at all. quizValidation’s decider rules (V1 missing_decider, V2 decider_bypass, V3 decider_optional, V4 unmapped_decider_answer) never inspect question_type. The old safety came entirely from the mutations refusing to create the state. Lifting the guards leaves zero publish-side check — consider a V7 for conflicting per-answer routes on a multi-select decider.

8Build order

  1. Engine. resolveTarget’s collect + emit, plus the three comment corrections. Unit test: one selected mapped answer is shape-identical to today; two produce targetIds in authored order; click order does not change the result. Verify with the byte pin. This alone fixes the live truncation bug in §1.
  2. Guards. All five mutation/lib sites together — :157 and :262 in the same commit or the wizard silently no-ops. Then the four UI surfaces and the four strings.
  3. Routing. Decide §6, then implement. Option A is a Logic-tab call to routingConflicts and a row-level warning.
  4. Cell rendering. One chip, the clear ×, the cell as the control, the inert info branch. Ships on its own — a visual change over existing data.
  5. The pickers. Narrows first: it proves the chrome with no engine dependency. Then the picks picker as single-select radios.
  6. The tray. Cards, arming, replace-on-place, then the measured overflow last — it is the only piece that cannot be verified without a real viewport.

Steps 1 and 2 are invisible to merchants and behind the decider gate. Steps 4–6 are pure UI and depend on nothing above them, so they can run in parallel.

Engine

  • One mapped answer selected → the resolved object is byte-identical to today, with no targetIds key.
  • Three mapped answers selected → targetIds in the decider node’s authored order, deduped; the pool is their deduped union; targetShape is undefined.
  • Tick the same three in a different sequence → identical output.
  • Two answers mapped to the same bucket, both selected → one entry, and no targetIds key (length 1 after dedupe).
  • Anchor answer maps to a single-product bucket, plus one other selected → hero + grid, not the hero-only page.
  • A narrowing question on top of a union → the filter intersects the union.
  • A legacy doc (logic_model !== "decider") reaches none of it.

Interactive — screenshots, not DOM markers

A 200 plus DOM markers is not proof for popovers; a pointer-trapped overlay renders fine and is unclickable.

  1. Click a cell’s white space → the picker opens. Click inside it → it stays open.
  2. Pick a second recommendation for an answer that already has one → the first is replaced, and the cell only ever shows one chip.
  3. Arm a tray card, hover an occupied cell → it reads Replace {old} with {new}.
  4. Narrows: tick three values, Cancel → zero network writes. Watch the network panel.
  5. Narrows: remove one value with its × → the answer’s other filter families survive.
  6. Set a mapped Narrows question to Info and back → values survive byte-identically and render inert in between.
  7. Promote a multi-select question to Picks the result → it works, from all four surfaces.
  8. 200 recommendations → the tray still occupies two rows and See N more counts everything unseen. Resize narrow and wide → it re-measures both ways.
  9. Keyboard only: tab to a cell, Enter opens, Escape closes, the clear × is reachable with a visible focus ring.
  10. Publish with one deciding answer unmapped → the untargeted gate still blocks.
