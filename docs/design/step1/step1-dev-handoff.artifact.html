01 · Before you touch anything

Five rules. All have shipped-incident history, and two of them are the reason revision 1 of this document was wrong.

The dual-model split Quiz.logic_model: z.enum(["decider"]).optional() — absent means a legacy points/ladder doc. Every new behaviour here is decider-gated, and legacy docs stay byte-identical. New schema fields are .optional(), never .default() — a default rewrites every legacy doc on the next parse-save round trip.
Read shipped state off origin/main — twice over (a) Not the working tree. The local builder branch is far behind main and still carries Quicksand and pre-Quartz radius literals, so it looks as though the token swap never landed. It did. Use git show origin/main:<path>. This document is pinned to eaa4000 (2026-09-07); re-check anything load-bearing against current main.
(b) Not docs/design/brand-2026/quartz-tokens.css. That file is the handoff proposal. Its type ramp (42/38/26/16.5/14.5) is not what shipped — main ships 30/24/17/15/14/11. Revision 1 built §07 from the proposal and got every type size wrong.

The byte pin. After every deploy, curl -sS …/q/cmqqcb0ao004mqvkwjug7t0ya.json | shasum -a 256 must still start c02ccaec98a0fe9e. That is the dual-model invariant made checkable. Nothing here should change it; if it changes, stop.

The gate chain, unpiped, before every commit. A ; chain once shipped type errors that 500’d production SSR.
npm run typecheck && npm test -- --run && npm run build && npm run lint && node scripts/check-tokens.mjs

The behaviour reference is the mock at scratchpad/step1-tweaks.html — a self-contained page with 40 numbered changes and inline rationale. Where it and this document differ, this document is later; §06 and §08 name the two places they deliberately diverge.

Deliberately unchanged — do not touch The page heading, the card and row chrome beyond what §03 lists, the Preview results page footer, the row preview modal, the tab strip’s roving-tabindex tablist keyboard handling (RecommendationBucketsStage.tsx:255+ — already correct, do not respecify), and .qz-picklist (quizocalypse.css:781), which belongs to the separate “+ Add” picker dialog.

02 · Server & loader changes

Six changes below the component, two of which are live data-loss bugs that exist today independent of any redesign. Everything in §03–§06 is presentation on top of these.

1 · Ship status and variant data in the picker payload

ServerPayload

catalogProducts ships id, title, imageUrl, price, description, tagKeys, collectionIds. Three fields are missing that the UI now depends on:

  • status — the builder index (:286) and the publish bake (quizPublish.ts:616) both carry it; the picker is the only surface that does not. Without it a merchant can pick a draft, watch it land in Results looking like a real recommendation, publish, and never have it recommended.
  • variant options — variantOptionsOf() already exists and already drops Shopify’s placeholder Title: "Default Title", so “has real variants” is a well-defined question.
  • per-variant availability — for the variant preview’s in-stock / sold-out column.

The catalog block is ungated (:415 sits outside the stage gates that guard questionBuilder at :295 and recPage at :311) and the underlying read has no take/select/cursor, which is why descriptions are already sliced to 220 chars at :161-163. Add a response-size budget assertion with the new fields; do not rely on eyeballing it.

funnelLoader.server.ts:155–169 catalogProducts · :286 builder index · quizPublish.ts:616 — copy the derivation, no drift

2 · Allow a heterogeneous selection

ServerUI

A merchant can hold products, tags, collections and custom groups at once. Persistence never required otherwise — each bucket is one Category row, and addBuckets/removeBuckets are per-row and additive. But three intent guards and one client modal do enforce it, so this is four edits, not the two revision 1 claimed:

  • funnelIntents.server.ts:216 (toggle-bucket / select-all / clear-visible), :277 (set-buckets), :325 (switch-tab) each reject anything outside the three-member union.
  • switchTab opens TabLockModal and posts clear=true, which runs clearBuckets(). Delete the modal and the flag.
The key is logical, not enforced(shopId, quizId, source, sourceRef) has no @@unique in schema.prisma. It is held by addBuckets’ deleteMany-then-create transaction (step1Build.server.ts:112-119), so a concurrent writer can still create a duplicate. Do not go looking for the constraint.

3 · Fix the two live bugs in set-buckets

ServerData loss

leaverIds is computed as everything not in wanted (:292), and existing is selected at :286-289 with no discoveryRunId in the where or the select. That is two defects, not one:

  • Cross-type collateral — wanted is single-typed, so applying a suggestion deletes the merchant’s picks of every other type.
  • Logic-tab rule targets — api.categories.ensure-targets.tsx:115-127 writes rows with discoveryRunId: \`logic-tab-${quizId}\`. Those are real leaver candidates here. Deleting one dangles every rule that points at it and hard-blocks publish. Type-scoping alone does not fix this: a same-type Logic-tab target is still deleted.

Both, together:

existing.filter((c) => normSource(c.source) === rawType && !staysFor(c) && !c.discoveryRunId.startsWith("logic-tab-"))

Add discoveryRunId: true to the select at :288. It is non-nullable in schema.prisma, so no optional chaining.

Revision 1 got this half-right, and that is worse than wrong It prescribed the type-scoping only, and attached a “keep the exemption” note to clearBuckets — which is the one function that already has the exemption (step1Build.server.ts:139, alongside persistConfirmedGroups at :63). set-buckets has never had it. A dev following revision 1 would have believed this bug closed while shipping the publish-blocking half.

4 · Never overwrite a non-empty selection

ServerData loss

The goal pre-pick calls clearBuckets twice while the picker is live: goalPrepick.server.ts:62 on begin, and :207 again before addBuckets (“clearing again keeps a Retry honest”). Anything the merchant picks while goal_first.prepick === "picking" is destroyed when the job lands, and retry-gen re-runs it. The stalled state actively tells the merchant to pick their own products, then deletes that work.

Gate both calls: the pre-pick may write buckets only when the selection is empty. If it is non-empty, land as ready, leave the selection alone, and let the merchant Apply from the pill in §05. retry-gen takes the same gate.

This is the bug the whole arrival redesign exists to fix. Ship it with the tweaks, not after them.

goalPrepick.server.ts:62 beginGoalFirstFlow, :207 the pick handler · the retry-gen intent · step1Funnel.server.ts genStalled (~200 s updatedAt)

5 · Admit a fourth bucket type

ServerBlocks §03

The Custom tab persists nothing today. The Category system, GroupWizard, /studio/groups and groupMembership.ts all ship — but the bucket type does not, and six places reject a fourth:

  • BucketType is a closed three-member union — bucketPersist.ts:16, duplicated verbatim at stagesShared.tsx:22.
  • Three intent guards 400 on anything else — funnelIntents.server.ts:216, :277, :325.
  • BROWSER_SOURCES (funnelLoader.server.ts:175) filters a custom-sourced row out of the shelf.
  • bucketRowFor (bucketPersist.ts:29) has no branch that resolves one.
  • The tab cannot be remembered: bucket_browser.active_tab is z.enum(["product","tag","collection"]) (quizSchema.ts:1640).

Widen all six. The Zod change is a widening of an existing .optional() field, so legacy docs stay byte-identical and no Prisma migration is needed.

Two contracts to settle before writing any of it (a) Key identity. The row must be source: "group", sourceRef: <Category id>. Wizard groups are currently created with sourceRef: null and source: dominantSource(membership), which returns "tag" for any group containing tags (studio.groups.tsx:184-195, groupMembership.ts:82). Reuse that and the type-scoped delete in item 3 will treat a custom group as a tag and delete it.
(b) Bake resolution. Publish must resolve a group bucket through its stored productIds — the same path a collection takes (bucketRowFor → quizPublish.ts:524-538).

6 · Ship a deliverable count for the rail

ServerScoped by decision 8

“Group of 44 products” counts every member. The runtime filters the pool through isSellable (recommendationEngine.ts:122), which drops non-active products on any bake that carries status (new publishes; older bakes have no status and keep their exact pre-fix behaviour) and drops anything both out of stock and priced ≤ 0. So a group advertised as 44 can deliver 38.

Decision 8 settled how to say that: by context. The picker keeps the group’s real size — it is browsing a catalogue and 44 is true. The rail shows what the quiz will return, because that is the question it answers.

What to build. One field: a deliverableCount per bucket, computed server-side in the loader where full Product rows are already in hand (funnelLoader.server.ts:41). Derive it through isSellable itself, not through a status test — status alone is closer, not equal, because of the $0-and-out-of-stock rule. Render it in the rail only (§04).

Why not fix the count everywhere Because there is no single place to fix it. git grep -n "productIds\.length" origin/main -- app/ returns ~50 hits across ~25 files, each writing its own expression, and the Logic tab’s counts are not Category-derived at all — they are tallied from productIndex (QuestionWindow.tsx:320-358). Decision 8 avoids that migration rather than paying for it. If a later surface needs the honest number, lift the loader’s derivation into a shared deliverableCount(category, products) rather than writing a second expression.
funnelLoader.server.ts:41 the product read, :182 the current raw count · recommendationEngine.ts:118–129 isSellable · rail render (§04)

03 · The picker

Left panel: tabs, toolbar, list, footer. Geometry is pinned to the shipped stylesheet — see §07.

Tabs

  • Four tabs: Products · Tags · Collections · Custom. Custom requires §02 item 5 first — it cannot persist without it.
  • A tab prints its own picks and nothing else — Tags 9. Not the catalogue total: at the live 588px picker width, four tabs each printing a total plus the AI pill overflows by 52px, and the fix bought back only 21px. Totals live in each tab’s aria-label.
  • Switching tabs never touches the selection. A tab is a view, not a mode.
  • The Custom rename is tab-label only. Sentences still say group — “Add all 2 groups?”, New group, Group of 38 products. A find-and-replace produces “Add all 2 customs?” and a “Search custom…” placeholder. The placeholder takes the plural noun.
  • Focus must not imitate selection. A selected row is --qz-accent-tint fill + --qz-accent border (:2051 — not --qz-accent-wash, whose own comment says “selected rows” and will be picked by mistake). Focus is a dark --qz-ink outline. Fields keep the Quartz accent ring, which is what .qz-input:focus already does. See the specificity trap in §10 — a bare class selector loses to the global rule.

Toolbar — search · sort · one button

  • Sort is a native <select>, not a popover. Per-tab: Tags and Custom get Most products · Fewest products · A–Z · Z–A; Products and Collections get A–Z · Z–A only — a product has no member count, and a collection is something you already know the name of. (Collections is pending decision 4.)
  • Selected-first is a grouping, and it has two unstated rules. The sort runs inside each group. (a) The order is frozen between rebuilds — load, tab change, search, sort change — because re-partitioning on every toggle teleports the clicked row to the top and slides the next row under the cursor. (b) While a search is active the frozen order is bypassed entirely: the result is a flat sorted list with selections interleaved. Without (b) a dev implements selected-first unconditionally and diverges on every search.
  • Status filter — Active · Draft · Archived · All statuses. Active is the default because it is the only state the runtime surfaces. Products only; the other three tabs have no Shopify status, so the control is not rendered there rather than rendered dead.
  • Select all / Clear all — one control, no menu, and it always confirms. It acts on the loaded window, not the whole filtered set. The dialog counts what will actually change: with 9 of the 25 loaded rows already picked it offers Add 16, not Add 25. Clear all removes the whole window. With nothing in the window — a search with no matches — the control is disabled, so it never offers Select all 0. Under a partially-loaded list the dialog names the remainder: “That is everything currently shown — expand the list to reach the other 283.”
  • Both selects carry fixed widths. A <select> sizes to its chosen option, so without them the search field jumps every time the sort changes.

Rows

  • One line each. Today’s row is thumb + name + SUB_LABEL second line + check glyph + price (products) / count-link (RecommendationBucketsStage.tsx:580-625). Explicitly: the 42px thumbnail stays; the SUB_LABEL second line goes; the check glyph goes; the price goes; the count-link is replaced per the next bullet. What remains is a name and one right-hand column.
  • The picker’s count is the group’s real size and does not change (decision 8) — Group of 44 products, all members. The deliverable number lives in the rail only (§04).
  • The right column is flush to the row’s right edge on every tab and carries: Group of 13 products for groups, the variant list (Size · S, M, L, XL) for products. A single-variant product shows nothing — not a dash. A long variant list fades on the left, because the column is right-aligned.
  • The count is the control — View → is deleted and the underlined number opens the members. This applies to list rows and the AI Picks dialog only. In the rail the row itself is the control and the count stays plain text (§04) — read literally the other way, this sentence tells you to nest a button inside a role="button", which is the trap §10 records as hit three times.
  • The count button needs an accessible name: aria-label="View the 3 products in acne". The visible text alone leaves “13 products” as the accessible name for every row.
  • Selection is border + tint only — no tick. See §09 decision 1.
  • Draft and archived products carry a status badge; active products do not. Marking the exception is legible; marking the rule is 25 rows all shouting ACTIVE.

List & footer

  • 25 rows load; reaching the bottom loads 25 more. No Expand button. The list keeps live’s max-height: 460px and scrolls internally, so the widget and its footer stay on screen at any catalogue size.
  • The footer is one left-aligned line: Showing 25 of 308 active · 20 draft, 11 archived not shown. The underlined part is also the control — it switches to All statuses. It appends “ matching” under an active search. The ledger renders on Products only, and only for statuses not currently shown; on the other tabs the footer is a bare Showing N of M.
  • Filtered to Active, the row badge only fires on rows the merchant cannot see. Without the ledger they have no way to learn drafts exist. This line is the answer to “where do I see Active vs Draft”.
  • No count of what is left. Showing 25 of 308 already carries it.

The narrowing line — the one genuinely new element

Shown once above the list, not per row; absent on the Products tab; opens an explainer modal. Copy is pending decision 6. Its insertion has a layout trap — see §10.

States that must be specified before build

  • Empty or still-syncing catalogue — a fresh install hits this on the funnel’s first screen.
  • The Custom tab is empty for every shop until someone builds a group, so its empty state must be the New-group affordance, not a message beside one.
  • Zero search matches, and a status filter with zero matches — including the ledger’s grammar when both trailing counts are zero and the underlined control has nothing to switch to.
  • A selected row that the current filter or search excludes. Status defaults to Active, so a previously-picked draft stays in the rail but leaves the list; Clear all acts on the loaded window and cannot reach it; the rail has no status badge, so the pick looks healthy; the ledger counts unshown rows, never unshown picks. Pick one rule: selected rows are always shown regardless of filter, or the rail carries the badge and the ledger counts hidden picks.

Accessibility this document introduces

  • Deleting the Expand button removes the only keyboard route past row 25 — scroll-triggered loading never fires from focus movement. Either focus reaching the last row also loads, or a visually quiet “load more” stays for keyboard and AT.
  • No live-region spec for 25 appended rows, or for the self-rewriting ledger — which is also a control and needs an element type and accessible name.
  • Focus return after each modal close, after ✕ removes a rail row, and after Apply (where Undo appears elsewhere on screen).
  • Esc from the members preview returns to the AI dialog, not the page — §05 specifies only the Cancel path, which is exactly the mouse-tested / keyboard-untested split that shipped broken in the mock.

04 · The Results rail

  • Titled Results, with a composition sub-line: 9 groups · 2 products. Your recommendations · 11 never said whether 11 meant eleven products or eleven sets of forty. The header keeps its total count badge on the right of the same row — title, sub-line and badge, not the sub-line alone.
  • Sections are Groups and Products — not the four source tabs. The tab a thing came from is a fact about the merchant’s route, not about the quiz. Section headers render only when both kinds are present, each with its own count.
  • The rail’s count is the deliverable one (decision 8, §02 item 6) — and the two numbers must not read as a contradiction with the picker. Copy rule: when deliverable equals total, print 44 products. When they differ, print 38 of 44 products. That form shows the gap and explains itself, needs no extra sentence, and appears only where the merchant is looking at output.
  • Non-product buckets use the glyph, never a member’s photo. Today cardFor/cardsForTab give four tags one shared picture and render “dryness” as a red square.
  • Rows open the same preview as the list. The row must be a div role="button", never a <button> — it contains the ✕, and the ✕ resolves first. The count inside it stays plain text.
  • A pick confirms itself: the row that just landed flashes and the rail scrolls it into its own frame. Set scrollTop on the rail list directly — scrollIntoView moves the page too. Bulk actions skip the flash.
  • The five-row cut is measured from the fifth real row, not calculated: section headers make any fixed-pitch arithmetic wrong. The list still scrolls (overflow-y: auto, :3423) — the fade marks continuation, it does not truncate access. No count line under it.
  • Keep the shipped accent-tinted border, violet shadow and position: sticky — those are deliberate, not drift.

05 · AI Picks

Two shipped surfaces collapse into one pill. Naming them correctly matters — revision 1 pointed at the wrong component and lost four states.

Which surfaces, and which AI The pill replaces both the inline tip row .qz-rb-tiprow (RecommendationBucketsStage.tsx:442–484 — ✦ / Tip / Use this / Applied / Undo / ✕) and GoalFirstBanner (:1185–1302), which are mutually exclusive via !goalFirst at :430. Revision 1 cited only GoalFirstBanner and described the tip row’s controls, which that component does not have.

They are also two different AIs. “AI Picks” as specified here is the deterministic heuristic in bucketDetect.ts; goalPrepick.server.ts is the genuinely-AI goal pre-pick. The pill must not attribute picks to the goal unless goal_first.prepick produced them.

Four states, not two

Inheriting GoalFirstBanner means inheriting its lifecycle. Specify copy for each: picking (a detached gen job is in flight — say what the picker can be used for meanwhile, and that existing picks are kept), stalled (the genStalled ~200 s updatedAt backstop, with Try again → retry-gen), failed (with Try again), and ready / applied. Dropping the first three changes the AI’s identity halfway through the flow and removes the only retry path.

The dialog

  • Titled AI Picks, sub-lined Based on “…the goal…”. The goal moves out of the body, where it competed with the list; it is provenance, so it belongs with the title.
  • Each row’s count opens that item’s members. A count of one shows nothing at all — the row already names the only thing in it.
  • Apply → Applied (disabled), with Revert beside it.
  • The Override confirm fires on an existing selection of the type being applied — not on any selection. A merchant holding only products, when the suggestion is tags, has nothing replaced and should fall straight through. Implemented as “an existing selection blocks”, the dialog fires reading “0 tags are already selected”. Its Cancel returns to the AI dialog, not the page.
Apply and revert are scoped to apply.type — both of them The suggestion is not always tags. suggestBucketStrategy returns suggestedType: "product" with applyFromProducts() below SMALL_CATALOG, and has a collection branch above it — apply.type is product | tag | collection (bucketDetect.ts:110-146). A tag-scoped Apply is wrong for two of three cases, including the small-catalogue shape most new installs have.

Apply replaces that one type’s half of the selection and leaves the other three alone. Revert must be scoped identically — delete the suggested type’s keys, restore the keys of that same type that were selected before. Restoring a whole-selection snapshot silently discards anything added since the apply: the same stale-state-over-newer-intent bug as §02 item 4 and the undo window below. It arrived by three separate routes in one design pass; assume a fourth.

Revert and Undo — three invalidation rules

  • Revert needs two conditions: the picks are still selected and a prior-key snapshot exists from an apply in this session. With the picks pre-selected and no snapshot — the opening state, and every return visit — the dialog shows a disabled Applied and no Revert. Decide whether the prior keys persist or Revert is explicitly session-scoped, and say which.
  • The 5 s Undo is cleared immediately by any row toggle and by either direction of Select all / Clear all, because the snapshot it would restore is stale. That invalidation is what actually bounds the risk decision 2 debates.
  • Applying force-switches the picker to the suggested type’s tab and clears the search.

Loader payload growthThree fields × catalogue size, on an ungated, uncapped read (:415, no take/select/cursor at :41). The loader already slices descriptions to 220 chars for exactly this reason. Add a size-budget assertion, not a manual check.

Deliberately not built

Most-specific-wins subtraction. When a product is picked and a group containing it is picked, one result becomes a strict subset of another. We considered subtracting at bake time and decided against it: overlap predates multi-type selection (two tags have always shared products), subtraction is the app silently editing stated intent, and it introduces an emptied-group failure mode that does not exist today. applyRuleAction("hide") already expresses it per-branch for merchants who want it.

What would change the decision: measure it. Count published quizzes where one target’s members are a subset of another’s. If it is rare, a warning is enough permanently.

1 · Selection is carried by colour alone

Decide

Dropping the tick leaves border + tint as the only signal — a WCAG 1.4.1 problem for sighted colour-blind merchants (aria-checked covers screen readers, so that is not the exposure). Recommendation: if it needs a second channel, make it border weight — 2px selected against 1px unselected. Non-chromatic, costs no ink, does not bring the glyph back.

2 · The undo window is 5 seconds

Decide

What is being undone is a change to the rail, and glancing right to see what moved costs a couple of seconds. Note the risk is already bounded by the invalidation rules in §05 — any edit clears the snapshot. Recommendation: 8–10 s, or “until the next click anywhere”. Five ships unless you say otherwise.

3 · Should dismissal persist at all?

Decide

Revision 1 stated this backwards. Today the ✕ dismisses for the session only — dismissTip writes sessionStorage (RecommendationBucketsStage.tsx:186-189, key qz-rb-nb-${quizId}) with no server write. banner_dismissed (quizSchema.ts:1641) is read at :87 but honoured only as a legacy value, and its sole writer has no client caller. A new session brings the tip back. Making the pill one-way per quiz is a behaviour change requiring a rebuilt write path. Decide whether dismissal should persist, and whether a route back to the picks is needed either way.

4 · Collections lost their size sorts

Decide

Collections now offer A–Z / Z–A only. Most products was the shipped default there and size is not meaningless on an 18-collection list. One array entry to restore if merchants turn out to use it.

Decide

6 · The narrowing line overpromises

Decide

“Groups can be narrowed by a later question” is false for a group that resolves to one multi-variant product — a narrowing question cannot reduce a one-product pool. Shown once and hidden on Products, which limits the damage without fixing the sentence. Recommendation: reword to name the condition, or suppress it when every picked group has one member.

7 · Mixed selection produces mixed result-page shapes

Settled · accept

A product-sourced target bakes as target_index.type: "product" and renders hero-only, no grid; tag and collection targets render hero + grid. Today’s forced homogeneity means every result page in a quiz looks the same. Allowing mixed selection means one quiz can serve both shapes depending on the answer. Settled: accepted. A one-product result should look different — there is nothing to put in a grid. No runtime or bake work; this is current engine behaviour, newly visible. §02 item 2 and §03 are unblocked.

It is also a temporary call, not a permanent one — see §12. Result-page mapping will make shape an explicit per-result choice and replace this derivation outright, which is why no new code may derive presentation from source in the meantime.

8 · What number should a group count show?

Settled · split by context

Settled: the number depends on which question the surface is answering.

  • The picker shows the group’s real size — Group of 44 products. You are browsing a catalogue, and 44 is a true fact about that tag. Unchanged from today; no work.
  • The rail shows what the quiz will actually return. You are looking at output, so the number must be the one isSellable will pass.

This drops §02 item 6 from a ~25-file migration to one loader field and one render site. See §02 item 6 for the shape, and §04 for the copy rule that keeps the two numbers from reading as a contradiction.

12 · Known future work

Not in scope. Listed because each one changes what a decision here is worth, and because building too tightly against today’s shape makes them expensive later.

Result-page mapping, by result selection

Planned

A merchant will eventually choose the result page per recommendation, rather than having it implied by what kind of bucket the recommendation is.

Why it matters to work happening now. Today the shape is implicit and derived: publish bakes target_index.type from the bucket’s source (quizPublish.ts:539-542), and the runtime branches on it — a product-shaped target renders hero-only with an empty grid (recommendDecider.ts:395) while tag and collection targets render hero + grid. Decision 7 exists only because heterogeneous selection makes that implicit rule visible for the first time.

The one instruction that follows from this Do not add new logic that derives presentation from source, and do not let “product means hero-only” leak into any new call site. Keep the existing derivation exactly where it is, in the bake. When mapping lands, shape becomes an explicit stored field and that single derivation is the only thing that has to give way — provided nothing else has started copying it.

What it makes cheap. Decision 7 stops being permanent. If mixed shapes turn out to bother anyone, mapping is the fix — so accepting them now only has to hold until then.

The per-page AI surface

Planned

The advisories removed in §08 are destined for a per-page AI surface that can hold all of them and be argued with — which a paragraph wedged under a rail cannot.

Preserve two things on the way out. The one-recommendation notice ships today (RecommendationBucketsStage.tsx:704-709), so removing it is a live regression — keep its copy verbatim. And keep the containment detection written down: a selected product is either inside a selected group or it is not, which is cheap and should not need re-deriving.

Do not let the 25-recommendation ceiling come back with them. It counted recommendations and never looked at their membership, which is why it fired hardest on the merchants with the largest catalogues.

Out-of-stock behaviour, configured per result

Planned

oos_behavior exists in the schema and the runtime does not read it — recommendDecider.ts:386-417 applies a hardcoded stock policy. Per-variant availability already exists on the product card, and the runtime already swaps the CTA for email capture on a sold-out variant.

§03 surfaces per-variant stock in the picker’s variant preview for the first time. That is display only. It must not start implying a configurability the engine does not yet have.
