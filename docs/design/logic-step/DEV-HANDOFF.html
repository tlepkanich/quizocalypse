3 The rule model — read this before writing any UI

There are three places and / or appear. They are different scopes and the design keeps exactly one control for each.

ScopeControlEngine today
Between picks in one questionor between the chips; clickable to and only on multi-selectNot expressible. Two is conditions on one question AND together, so the pair matches nobody.
Between different questionsmatch all / match any, top right, once per rulematch all only — ruleMatches is conditions.every(...).
Between rulesThe ledger. Two rules with the same action is the outer OR.Shipped.
There is no in-rule grouping and there must not be. (A and B) or (C and D) is two rules with the same action. Brackets, boxes and per-pair operators were all tried and removed — they add no expressiveness and reintroduce precedence.

Two engine behaviours the UI must surface

op: "is_not"

Shipped in DecisionRuleCondition and unreachable from any UI until now. Exposed as an is / is not toggle per condition column. Without it a merchant expresses negation by listing every other answer, which silently stops covering the question when an answer is added later.

First match wins

recommendDecider.ts:199 — rules are checked in array order and evaluation stops at the first match. Array position is priority. The ledger numbers rules, allows drag-reorder, states checked top down, and flags a rule that can never be reached.

5 What changes for the AI — the biggest finding

No code path in the app ever writes role: "filter". filterMatching.ts:30 states it outright. The narrowing role — the entire basis of Attributes + Rules — is set only by hand in the Logic tab. Every AI-built quiz arrives with narrowing unset.
PathWritesResult in Logic

The prompt actively works against narrowing

generation.ts:420–421 instructs the model:

“Every OTHER question is a qualifier that refines the recommendation but must NOT try to route — keep qualifier answers' tags light.”

In the new model those are exactly the questions that should carry rich answer→value mappings. Three things follow:

  1. Add role to the generation tool schema so the model can mark a question as narrowing.
  2. Rewrite that instruction — narrowing answers want accurate catalog values, not light tags.
  3. Decide the fallback for quizzes already generated without roles: either infer on first open of Logic (a question whose answers carry catalog tags is a narrowing candidate) or leave every role unset and let the merchant assign. Owner decision, not a code detail.

6 Written rules (paste)

Its own entry point — + Paste rules beside + Add rule on the ledger, not a tab inside the modal. A confirmed paste writes the same decision_rules, so a pasted rule opens in the builder for editing.

when A necklace then pin Gift cards
when A ring or A bracelet then pin Gift cards
when Warm golds and A necklace then show Necklace
when A necklace or A ring and Warm golds or Silver tones then pin Gift cards

No brackets. The parser resolves scope from which question each answer belongs to: or between answers of the same question is within-column; and between different questions sets the rule operator. Mixing and with or across questions has no single reading and is listed as unmatched, never guessed at.

Parser requirement that has already bitten: resolve answer names longest-whole-match-first. Splitting on a bare “and” cuts inside real answer names — “Controlling shine and pores” is one answer.

9 Build order

  1. Fix the index gaps. Split list-typed metafields (type is already on the raw value, a list.* check is enough) and bake status. Decide vendor in or out. Unblocks the value picker, the catalog strip, the not-live gate.
  2. The attribute read-out. Cluster sources holding the same fact, grade each, demote copy and identifiers. A pure function over the index — unit-testable before any UI exists. Every other module reads from it.
  3. Engine: OR. Three related changes — match any across conditions, or between answers of one question, all of on multi-select. All are ruleMatches and its callers. Decider-gated; legacy docs byte-identical. Verify with the byte pin.
  4. Attributes + Rules end to end. Rail, header, mapping table, value picker, health line. Reuse filterAnswerMatchCount() and guessAnswerMappings().
  5. Rule surfaces. Builder over existing decision_rules, plus is / is not, ordered ledger with drag-reorder and shadow detection, paste, coverage sidebar.
  6. AI. Add role to the tool schema, rewrite the light-tags instruction, decide the fallback for already-generated quizzes.
  7. Chooser, style bar, gates. Last — each summarises state the earlier steps produce. Point based renders and does nothing.

10 The attribute read-out — full algorithm

Step 2 of the build order, and the largest net-new piece. This is not a sketch: the pipeline below was prototyped and run against all five real catalog exports (Made By Mary, two baby-clothing stores, hope&plum, EBY). The thresholds are the ones that survived that run — each exists because a specific real merge was wrong without it.

Pipeline: raw sources → pre-classify → cluster candidates → score. It is a pure function over the product index, so it can be unit-tested against fixture catalogs before any UI exists.

a. Build sources

One source per: tag family (fit:slim → family fit; bare tags are skipped), metafield key, variant option name, product type, vendor (once indexed). Normalise every value to trimmed lower-case; drop empties and anything matching /^\s*(n\/?a\.?|none|null|-|—)\s*$/i — this is bug 4. List-typed metafields split on comma; this is bug 1 and it must be fixed first or the source is one opaque string.

b. Pre-classify — before any clustering

VerdictTestWhy it exists
copymean value length > 40 charsMade By Mary's care_instructions contains the words “sterling silver”. Left in, it merges into the Metal attribute.
identifierV ≥ 4 and covered ≥ 4 and V / covered > 0.9Near-unique per product — SKUs, handles. Splits the catalog into groups of one.
candidateeverything elseOnly candidates enter clustering.

Where V = distinct values, covered = products carrying any value.

c. Cluster — union-find over value-space overlap

Compare every candidate pair. Split values into atoms on / and , first. Two atoms match when they are identical, or when they share a token of ≥ 5 characters and one token-set is a subset of the other. Pure numbers never token-match.

containment = hits / min(|A|, |B|)          // symmetric
merge when   containment ≥ 0.7  AND  hits ≥ 2
skip pairs where either side has < 2 atoms
The hits ≥ 2 guard is not optional. A one-value source scores containment 1.0 against anything it happens to touch. Without it, Made By Mary's customization_max_charms (“5.0”) merges into ring sizes, and hope&plum's “sierra” colorway merges into a product handle. Requiring two matched values kills both without weakening a real synonym cluster, which always overlaps on several.

d. Orphan absorption

A source with exactly one usable value can never clear the two-hit bar, but is often the same fact half-populated — EBY's color-pattern is “Nude” on one product and N/A on the rest, which is plainly Colour. Absorb those into a multi-value cluster on an exact value match only — never the token-subset rule, and never for a bare number.

e. Name, primary, grade

OutputRule
Display nameShortest label, preferring tag families, then variant options, then product type. filter_* keys are penalised — they are plumbing names.
Primary sourceThe one an answer actually writes to: most distinct values, then best coverage.
Gradecantsplit if V < 2 or every covered product carries every value · thin if covered < 60% of catalog · weak if the largest value covers > 90% of covered products · else good.

Sort attributes by grade, then by value count descending. Anything pre-classified as copy or identifier is reported separately as demoted, with the reason — the merchant should be able to see why a field they recognise is not offered.

A merged cluster must record its members. Mapping an answer writes to the primary, but matching unions across all members — which is exactly what productMatches() already does.

11 Shadow detection

The ledger flags a rule that can never fire. Because evaluation stops at the first match, rule B is unreachable when every path matching B also matches an earlier rule A.

A shadows B  ⟺  A is earlier in the array
                 AND every condition in A appears identically in B
                     (same question_id, answer_id AND op)

If A requires a subset of what B requires, anything satisfying B satisfies A, so A always wins. O(rules² × conditions) — trivial at any realistic rule count.

Deliberately conservative. This catches definite shadowing only, not every unreachable rule (contradictory conditions, for instance). That is the right trade: a false “never reached” on a working rule is far worse than a missed warning. Zero-condition rules are already handled separately — they never fire and are treated as half-built.
When match any ships the test inverts for those rules — an ANY rule matches more as it gains conditions, so a superset shadows rather than a subset. Do not reuse the ALL test on ANY rules; write the second case explicitly or skip ANY rules until it is written.

12 Rule lifecycle, and the two rules arrays

Edit and duplicate

The shipped ledger offers delete and nothing else, so a single wrong condition means rebuild from scratch. Both surfaces are now in the mock:

  • Edit — opens the same builder pre-filled against the existing rule id. Same modal, same storage, no second code path.
  • Duplicate — copies the rule and inserts the copy directly below the original, then opens it. Position is priority, so appending to the end would silently change which rule wins.

The deciding-question lockout

Exactly one question may be role: "decides". When another already holds it, the role menu keeps the option visible and disabled, names the holder, and offers Move it here — one action that demotes the current holder to filter and promotes this question. Enforce at write time, not only at publish. Hiding the option instead leaves a merchant hunting for a setting that appears to have vanished.
