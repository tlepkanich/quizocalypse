Wiskr · logic step

Every module in the logic step

The logic step only — nothing from recommendations or questions. All eighteen modules on one page, nothing behind a tab or a first-visit gate, so the whole surface is reviewable at once. Slots show what would be pulled in rather than one store's data, and each module lists its inputs by source. Every Shopify-native product surface is covered — metafields, tags, collections, variant options, types, vendors and individual products.

Authored

Written by the merchant elsewhere — question and answer text from the Questions step, result sets from Recommendations.

Catalog

Read from the synced Shopify catalog — attribute values, product counts, status.

Computed

Derived at render time. Never entered, never stored — counts, grades, coverage, the role a question resolves to.

Rule

Belongs to a rule — its verb, conditions and targets.

Group order is relevance. The attribute this question's other answers already use comes first, then whatever matches the answer's own words, then the rest.
What each source is
MetafieldsCustom and Shopify-standard namespaced fields — custom.*, shopify.*. The richest source, and the one most often half-populated.
TagsProduct tags. Family-shaped tags (fit:slim) become an attribute with values; bare tags stay single flags.
CollectionsManual and automated collection membership. Already a merchant-authored grouping, so it doubles as a result set.
OptionsShopify variant options — the Size / Color / Material axes on a product’s variants. Native to every store, and usually the cleanest size and colour data available.
TypesThe product Type field. Few values, high coverage — usually the best candidate for the deciding question.
VendorsThe Vendor field. Useful on multi-brand catalogues, inert on single-brand ones. Not indexed today — needs baking into the product index before it can match.
ProductsIndividual products chosen by hand. Not an attribute — it does not scale as the catalogue grows — but valid as a rule target or a small result set.
The toggle filters, it does not commit. A merchant never picks a source — a value that lives in three of these is one row, and mapping it matches products storing it in any of them. The toggle exists for the opposite case: “show me only what is in my metafields” while hunting for something.
Blocked on a bug fixThe blocker module. Two live bugs stop it working as drawn. (1) List-typed metafields are flattened to a single opaque JSON string by flattenMetafields() (productIndexing.ts:8), so a multi-value metafield can never be offered as separate values or matched. (2) Vendor is on Product (schema.prisma:116) but absent from IndexedProduct and from productMatches(), so a vendor mapping would silently match nothing. Fix both first, or drop the Vendors toggle from v1.

One operator, one place. The and under the columns is the rule’s join — clicking it makes the rule or, and the column footers carry the separate any of / all of choice that only means something on a multi-select question. An earlier draft had a match all selector in the band header as well; two controls for one piece of state is how they drift apart.
Columns are earned, not given. A question becomes a column only when the rule constrains it; the rest sit below as chips. That is what keeps the panel legible — a two-condition rule gets two wide columns instead of eight narrow ones, and it is also what lets the design survive a long quiz. Measured: at 20 questions the chip row is three lines tall, and a rule using six of them still fits without scrolling. Dropping a column with × returns it to the chips for the rest of the session.
Two operators, both editable. match all / match any across columns, and any of / all of inside a column — the second only means something on a multi-select question. One join per rule, so there is never an ambiguous mix without parentheses.
Net newNeeds the one net-new schema field in this whole design: a rules array carrying conditions, both operators, verb and targets. There is no join or operator concept in quizSchema.ts today. Add it .optional(), never .default() — a default rewrites every legacy doc on the next parse-save round-trip. Note the storage shape follows the UI here: a rule stores only the questions it constrains, so an unused question is an absent key rather than a stored “any” — which means adding a question to a quiz never has to touch existing rules.

Paste rules

The rule builder’s second tab — same modal, not a separate entry
Pulls in
  • AuthoredPasted text — whatever the merchant worked out elsewhere
  • AuthoredQuestion and answer text, to resolve each line against
  • ComputedWhich lines parsed, and which could not be matched
  • ComputedThe rules a confirmed paste would create
One line, colour-coded back
when{answer}and{answer}→{verb}{target}
Every recognised part is tinted by what it resolved to, so a merchant can see the parse rather than trust it.
Nothing is guessed. Lines that resolve become draft rules the merchant confirms; anything unmatched is listed as unmatched and skipped. A near-miss is never silently snapped to the closest answer — that is the failure mode that makes paste untrustworthy.
Why it is a tab and not its own button. Build and Paste produce the same object; splitting them into separate entry points invites two rule stores and two mental models. The toggle lives in the modal header, and switching keeps whatever is already there.
Net newStorage is module 10’s — a confirmed paste writes exactly the same rules array, so this adds no schema. The net-new work is the parser, and the one requirement that matters: longest-whole-match-first when resolving answer text. Splitting on a bare “and” cuts inside real answer names (“Controlling shine and pores”), which is the bug this parser exists to avoid.

Build order

What to focus on, and why this sequence
  1. 1Fix the two index gaps Nothing above works properly until the product index carries what the UI claims it can read. Split list-typed metafields in flattenMetafields() (the type is already on the raw value, so a list.* check is enough), and bake status so the engine can drop non-active products. Decide separately whether vendor is in scope — if it is, it needs indexing too; if not, remove the Vendors toggle. Unblocks modules 02, 08, 15
  2. 2The attribute read-out The derivation every screen reads from: cluster sources that hold the same fact, grade each one, demote copy and identifiers. Not a screen — a pure function over the index, so it can be unit-tested before any UI exists. Module 16 · unblocks 01, 06, 08
  3. 3Attributes + Rules, end to end Rail, header, mapping table, value picker, health line. This is the path most catalogues take, and it leans hardest on work that already exists — reuse filterAnswerMatchCount() and guessAnswerMappings() rather than writing new counting. Modules 04, 05, 06, 07, 08
  4. 4Rules storage, then the rule surfaces One new optional schema field carries conditions, both operators, verb and targets. Land the schema and the mutations first; the ledger, builder, scaffold and coverage sidebar are all reads over it. Modules 09, 10, 12, 14, 17, 18
  5. 5Chooser, style bar, gates Last, because each one summarises state the earlier steps produce. The chooser needs the scan from step 2; the gates need counts from steps 3 and 4; the style bar only needs the guarantee that switching never discards a mapping. Modules 01, 02, 03, 15
Two invariants that outrank the design. Every new schema field is .optional(), never .default() — a default rewrites legacy docs on the next parse-save. And all of this is decider-gated: a doc without logic_model: "decider" must serialise byte-identically after these changes.
Real catalog, real numbers. Made By Mary — 28 products, read from an actual Shopify export. Every count is computed with the same union rule the engine uses, so Warm golds → 25 of 28 is the number a shopper would really narrow to. Nothing here needs clicking: every screen and overlay of the logic step is laid out in order, at the width the product actually runs at.
Sixteen modules, no interactivity and no store data — every value is a slot showing what would be pulled in. Colour marks the source: authored elsewhere, read from the catalog, computed at render, or belonging to a rule. States that only appear on failure (unset, zero-match, mixed, cannot-narrow, unused) are rendered alongside their healthy versions rather than left to be imagined.

Built on the Quartz Rail tokens: Figtree across every role including numerals, so labels take their distinction from case and tracking rather than a second face; radii at 4 / 6 / 8; --card-shadow: none, with elevation kept for overlays that genuinely float; accent #5B45D6 on a white ground with violet-tinted inks.
